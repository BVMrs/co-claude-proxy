# 2026-11-09 — End-to-end tests of the shim's SSE/response relay

## Question

The milestone is a working Claude Code session through `copilot_shim` against real Copilot.
The earlier lab (`rewrite-fuzz`) covered the request rewrite and listed the **response relay**
(`server._relay`) as not covered. Every Claude Code turn streams through that code. So:

> Is the relay transparent? Each SSE event must reach the client promptly and byte-exact,
> keep-alive must survive mixed responses, and when either side fails mid-stream the
> other side must see a failure, not a clean end, without the shim leaking or going silent.

## Method

`lab/sse-relay/` against `main` @ 960daf7 (no code changes). Python 3.13.12, Linux 6.12, loopback, 3 cores.

- `harness.py`: a **raw-socket scripted upstream**, which controls framing, timing, aborts
  and RSTs exactly. It sits behind the real `make_handler()`. A raw-socket client
  (`TCP_NODELAY`, like Node/undici) parses chunked framing itself and timestamps every
  `\n\n`-terminated event. Upstream and client share one monotonic clock, so latency
  = arrival − upstream `sendall` return.
- Real upstream framing: copilot-api serves Hono through `srvx` (`src/start.ts`) and streams
  with `streamSSE` (`src/routes/messages/handler.ts`). Under `npx`/Node that gives
  **`Transfer-Encoding: chunked`**, with no `ping` events and no abort handling. "Chunked"
  is therefore the realistic case. "Close-delimited" (no length, `Connection: close`, which is
  what `tests/fake_upstream.py` does) is the secondary one.
- Experiments (`run.py E1 E1b E2 E3 E4 E5 E6`; `probe_stderr.py` prints the abort/stall logs):
  - E1/E1b latency, 4 event-timing patterns × 2 framings × {direct, shim, shim+`TCP_NODELAY`}
  - E2 byte fidelity
  - E3 keep-alive
  - E4 client abort
  - E5 upstream failure
  - E6 chunked request body

Raw numbers: `lab/sse-relay/results-*.json`.

## Results

### E1/E1b: latency. Transparent; one narrow Nagle stall

Added per-event latency through the shim is about **+0.1 ms median and < 1 ms p99** for every
pattern (direct: p50 0.04–0.12 ms; shim: p50 0.11–0.30 ms, p99 0.24–0.76 ms). End-of-stream
(terminator) latency is ≤ 0.6 ms. All 15 600 E1 + 12 000 E1b shim events arrived complete.

The one anomaly is a stall of exactly the Linux delayed-ACK minimum (~40 ms). E1b, 2000 events per cell:

| pattern / framing | shim stalls > 10 ms | shim + `TCP_NODELAY` |
|---|---|---|
| burst of 4 back-to-back events every 50 ms / close-delimited | **13 / 2000 (0.65 %), 40.3–41.3 ms** | 0 / 2000 |
| same / chunked | 0 / 2000 | 0 / 2000 |
| pairs 0.3 ms apart every 30 ms / both | 0 / 4000 | 0 / 4000 |
| pairs 0.05 ms apart every 20 ms / both | 0 / 4000 | 0 / 4000 |

Cause: the shim never sets `TCP_NODELAY` on the client socket. When it writes a chunk while an
earlier one is still unacked, Nagle holds the second write until the client's delayed ACK
fires. This was **not observed with chunked upstream framing**, which is what copilot-api sends.
Impact is cosmetic: at most 40 ms on a token, and rare. The fix is one line in `Handler.setup`.

### E2: byte fidelity. 300 / 300 exact

The test used 300 streams (150 chunked, 150 close-delimited) totalling 6.9 MB. Events ran
from 1 B to 306 KB, with JSON holding `é漢字🙂`, escapes and newlines. Each stream was re-split
at up to 30 random byte offsets, some inside UTF-8 sequences, with random 1 ms gaps.
**0 failures**: the client's de-chunked bytes equal the upstream bytes, and every stream ends
with a terminator. `read1()` relaying never re-encodes anything, so this is as expected.

### E3: keep-alive. 30 / 30

There were 30 sequential requests on **one** client connection: SSE 200, JSON 200, 400, chunked 500,
204, HEAD, repeated. All framed correctly and none desynchronised. The shim opens **one new upstream
TCP connection per request** (30 for 30). That is fine for `localhost:4141` over plain HTTP.

### E4: client aborts mid-stream (Esc in Claude Code). Upstream lingers ≈ 2 inter-event gaps; a traceback for each abort

| upstream event gap | upstream sees the shim close it after |
|---|---|
| 20 ms | 42.9 ms |
| 500 ms | 1004 ms |

The shim only notices the client is gone when it next writes. The first write after the client's
FIN succeeds and draws an RST; the second raises `BrokenPipeError`. Only then does
`finally: conn.close()` close the upstream. So upstream generation continues for **up to two
upstream-silence periods**. copilot-api sends no pings, so during a long thinking or tool-input
pause that could be minutes. Every interrupt also prints a **full `BrokenPipeError` traceback** to
stderr through `socketserver.handle_error`. That is noise in exactly the log the HANDOVER asks
the user to read.

### E5: upstream failures. Truncation reaches the client correctly, but logging is uneven

| case | client sees | shim log at default level |
|---|---|---|
| chunked, upstream closes without `0\r\n\r\n` after 3 events | 200, 3 events, **truncated (no terminator)** ✔ | `IncompleteRead` traceback |
| RST mid-stream | 200, 1 event, truncated ✔ | `ConnectionResetError` traceback |
| close-delimited EOF after 3 events | 200, 3 events, **clean end** (inherent: indistinguishable) | nothing |
| close before response headers | **502** JSON error ✔ (2 ms) | `upstream … unreachable` error line |
| stall before headers (shim timeout 1 s) | 502 after 1.0 s ✔ | error line |
| **stall mid-stream** (shim timeout 1 s) | 200, 1 event, truncated after 1.0 s ✔ | **nothing**: `BaseHTTPRequestHandler.handle_one_request` catches `TimeoutError` and calls `log_error`, which the shim routes to `log.debug` |

The client-facing behaviour is right in every case: it sees truncation where truncation is
detectable, and a 502 before headers. But a mid-stream stall, which would occur after the default
**600 s** read timeout, is completely silent at INFO. That is the hardest failure to diagnose from the shim log.

### E6: chunked request body. Body dropped and connection poisoned

A `POST` with `Transfer-Encoding: chunked` and no `Content-Length` was tested. The shim reads 0 bytes,
forwards `POST` with `Content-Length: 0` and **an empty body** (upstream received 0 bytes), and
relays whatever the upstream says. The chunk bytes it never read then get parsed as the next request,
and the next request on that connection gets **no response (EOF)**. The Anthropic TS SDK sends a
string body with `Content-Length`, so Claude Code should never hit this. Other clients
(streamed `fetch` bodies, `curl -T -`) would.

## Summary

The relay is transparent on the realistic path (chunked upstream). It adds about 0.1 ms per
event, is byte-exact on 6.9 MB of adversarial splits, and keeps keep-alive intact. Upstream
truncation is propagated as truncation. The defects are all at the edges:
(1) client abort is detected late and logs a traceback;
(2) a mid-stream timeout is not logged at all;
(3) chunked request bodies are silently dropped;
(4) a rare 40 ms Nagle stall, close-delimited framing only.

## What the planner should do next

One small PR to `server.py` (~25 lines plus tests), independent of the real-Copilot capture.
It can sit with the `rewrite()` totality PR from `rewrite-fuzz`:

1. In `_relay`, catch `(BrokenPipeError, ConnectionResetError)` on client writes. Log one INFO line
   `path client disconnected after N bytes`, close the upstream, and return without a traceback.
   Catch `(http.client.IncompleteRead, OSError)` from `resp.read1` and log one WARNING
   `upstream ended mid-stream: …`. Then drop the connection *without* writing the terminator,
   which the current code already does by accident.
2. Override `log_error` to log at WARNING, so that `Request timed out` and malformed-request errors are visible.
3. Reject `Transfer-Encoding: chunked` request bodies with `411 Length Required` (simplest), or de-chunk them.
4. Optional: set `TCP_NODELAY` in `Handler.setup`.
5. Optional, for faster abort detection: while waiting on `read1`, `select()` on the client socket
   for EOF as well. That is only worth it if the real-Copilot session shows long silent gaps;
   copilot-api itself has no abort handling, so closing early may not stop Copilot generating anyway.
6. Tests: the scripted raw-socket upstream in `lab/sse-relay/harness.py` can be cut down into
   `tests/` (no network, loopback only). E3, E5 and E6 as regression tests run in < 3 s. E1/E2 are too slow for CI.
