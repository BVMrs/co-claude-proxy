# 2026-11-09: Shim under load: large bodies, concurrent streams, connection bursts

## Question

The milestone is a working Claude Code session through `copilot_shim` against real Copilot.
Earlier labs tested the rewrite (`rewrite-fuzz`), single-stream relay (`sse-relay`), translation
(`copilot-translate`) and cache cost (`cache-prefix`), all one request at a time. Real sessions
are not like that. Bodies grow to 0.5–4 MB (128k–1M-token contexts). Subagents, helper calls
and the main loop stream in parallel. The shim is a stdlib `ThreadingHTTPServer` that parses,
deep-copies and re-serializes every body under the GIL. So:

> Does the shim add meaningful latency, stall other streams, refuse connections or bloat
> memory at realistic body sizes and concurrency?

## Method

`lab/shim-load/` against `agents/lab` @ f91ed71 (shim code identical to 960daf7). No code
changes. Python 3.13.12, Linux 6.12, 3 cores, loopback only, no credentials.

- `bodies.py`: synthetic Claude Code bodies following the real shape captured in
  `lab/cache-prefix/capture_shape.json`. That means 3 system blocks, ~30 KB of tools, a
  `role:"system"` env message (so the shim always folds and re-serializes), and then
  `tool_use`/`tool_result` rounds of code text until a target size. Bodies are encoded like
  Node (`JSON.stringify`: compact, raw UTF-8). Token counts are approximated as bytes / 4.
- `upstream.py`: a fake copilot-api in its own process. It either streams chunked SSE on a
  fixed 20 ms schedule or returns small JSON after a delay. Its backlog is 256, so it is
  never the bottleneck.
- `shim_runner.py`: the real `serve()` / `make_handler()` in its own process. An optional
  backlog override is used for the fix check.
- `poster.py`: big-body sender in a separate process, so it shares no GIL with the stream
  readers.
- `bench.py E1…E5`; raw rows are in `lab/shim-load/results-*.json`.

The box is shared. Another project's simulation took 2 of 3 cores during an early pass.
Every number below comes from re-runs at load average < 0.8, with `loadavg1` recorded per E3
row. The early E4 run under load is kept as `results-E4-loaded.json`, and it agrees.

## Results

### E1/E2: per-request cost is linear and small, about 11 ms per MB

In-process cost of the shim's body path, median of 7 (E1):

| body | ≈ tokens | loads | rewrite (deepcopy + fold) | dumps | total |
|---|---|---|---|---|---|
| 58 KB | 15k | 0.19 ms | 0.52 | 0.24 | **0.95 ms** |
| 201 KB | 52k | 0.48 | 0.83 | 0.73 | **2.0** |
| 502 KB | 129k | 1.20 | 1.56 | 1.80 | **4.6** |
| 1.0 MB | 264k | 2.58 | 3.11 | 3.66 | **9.4** |
| 2.0 MB | 524k | 5.30 | 5.90 | 7.14 | **18.3** |
| 4.0 MB | 1.05M | 10.5 | 11.2 | 14.8 | **36.5** |

End-to-end added latency per request, shim minus direct, median of 15 (E2):
50 KB **+2.1 ms**, 200 KB +3.6, 500 KB +6.2, 1 MB **+11.4**, 2 MB +29, 4 MB **+46 ms**.
This is noise next to model time to first token, which is seconds for 100k+ token prompts.
A stripped prefill body costs the same as a passthrough one (1 MB: 8.6 vs 9.4 ms).

Side finding: `json.dumps(res.body)` uses Python's defaults, `ensure_ascii=True` and
`", "` separators. An ASCII body grows by 0.4–1.6 %. A body with CJK text grows by **+59 %**
(1.06 MB → 1.68 MB), because every non-ASCII character becomes a 6-byte `\uXXXX` escape.
The token count is unchanged, since copilot-api decodes the JSON. This costs only bytes and
a few ms on loopback.

### E3: big rewrites stall other streams by tens of ms (GIL head-of-line)

Setup: 6 SSE streams, each with events every 20 ms for 3 s. Meanwhile a separate process
sends large non-streaming bodies through the same server. The metric is the extra
inter-event gap, beyond the 20 ms schedule, across 888 gaps per run. 3 reps each:

| background load | path | extra gap p99 | extra gap max | gaps > 10 ms |
|---|---|---|---|---|
| none | direct / shim | 0.1 / 0.2 ms | ≤ 2.5 / ≤ 0.6 ms | 0 / 0 |
| 4 MB every 0.5 s (1 sender, realistic upper bound) | direct | 0.2 ms | ≤ 0.7 ms | 0 |
| | **shim** | **27–28 ms** | **39–78 ms** | 38–50 |
| 4 MB every 0.5 s × 3 senders | shim | 58–60 ms | 82–143 ms | 61–92 |
| 1 MB back-to-back (saturating) | shim | 13–17 ms | 17–24 ms | 23–52 |
| 4 MB back-to-back (saturating) | shim | 36–52 ms | 64–77 ms | 228–239 |
| 4 MB back-to-back × 3 | shim | 102–114 ms | 139–156 ms | 192–220 |
| (any of the above) | direct | ≤ 20 ms | ≤ 21 ms | ≤ 21 |

- Each large body freezes every other relay thread for roughly its own E1 cost. `json.loads`
  and `json.dumps` hold the GIL for 10–15 ms per 4 MB, and `deepcopy` adds GIL convoy effects
  on top.
- Saturated, the shim handles about 16 × 4 MB requests/s (≈ 65 MB/s) whether there are 1 or
  3 senders. It is single-core bound.
- In a real session a 1 MB body arrives every few seconds at most, which means a pause of
  ≤ 15–25 ms in other agents' token streams. That is visible only to instrumentation.
- **Not worth fixing now.** The only case where this matters is many parallel subagents with
  1M-token contexts.

### E4: the default listen backlog of 5 turns connection bursts into 1–28 s stalls (real defect)

The shim's `serve()` keeps `socketserver.TCPServer.request_queue_size = 5`, Python's default.
copilot-api, which runs on Node, listens with a backlog of 511. In the test, N clients connect
at the same instant (barrier) and each sends a small request. Upstream holds each request for
300 ms. Quiet-machine run (`results-E4.json`):

| N simultaneous new connections | direct | shim (backlog 5) | shim, backlog 128 | shim + one 4 MB body in flight |
|---|---|---|---|---|
| 8 | 0 stalled, max 303 ms | 0 stalled | 0, max 306 ms | **1 stalled, max 1332 ms** |
| 16 | 0, max 308 ms | **5 stalled, max 1346 ms** | 0, max 312 ms | **8, max 1571 ms** |
| 32 | 0, max 321 ms | **21, max 1757 ms** | 0, max 325 ms | **26, max 2170 ms** |
| 64 | 0, max 330 ms | **43, max 7949 ms** | 0, max 359 ms | **54, max 27 975 ms** |

"Stalled" means `connect()` took ≥ 0.9 s.

The run under load (`results-E4-loaded.json`) is worse: 1 of 8 stalls even without a big body.

- **Mechanism.** The single accept thread falls behind: it spawns a thread per connection,
  under the GIL, and stalls further while a big body is being parsed. The kernel's accept
  queue overflows. Linux then drops the SYN (client retries after 1 s) or the final ACK (the
  server retransmits SYN-ACK with exponential backoff: 1, 2, 4, 8 … s). That explains the
  ~1.05 s connect plateau and the 8 s and 28 s tails.
- **Fix.** Overriding `request_queue_size = 128` removed every stall: 0 / 120 across all
  N up to 64. All requests still eventually succeeded (`ok` = N everywhere), so the failure
  shows up as long pauses, not errors.
- **Exposure.** Claude Code is Node/undici with a keep-alive pool, so new connections
  burst only when the pool has to grow. That happens at startup, where several helper and
  main calls go out at once, and on parallel subagent fan-out, where each concurrent stream
  needs its own HTTP/1.1 connection. 8 simultaneous connects with one large in-flight body is
  a plausible fan-out moment, and it already stalled once. I could not run a real Claude Code
  binary in this sandbox to count its actual burst size; that is the open item.

### E5: memory is about 4 × body per in-flight request

Peak RSS by `ps` sampling. Idle RSS is 22.7 MiB.

- 1 MB bodies: 1 / 4 / 8 / 16 concurrent → 26 / 40 / 57 / **96 MiB**, ≈ 4.2 MiB each.
- 4 MB bodies: 1 / 4 / 8 / 16 concurrent → 33 / 80 / 145 / **295 MiB**, ≈ 15 MiB each.

The four copies are the raw bytes, the parsed dict, the deepcopy and the re-encoded bytes.
That is fine on a workstation. If memory ever matters, dropping the `deepcopy` (parse a
fresh dict and mutate it) removes one copy and about 30 % of E1's time.

Methodology note: `ru_maxrss` is not usable for a child process here, because Linux carries
the parent's peak across fork+exec. The first E5 attempt reported a 40–61 MiB "idle" peak
for that reason and was discarded.

## Sources

- CPython `Lib/socketserver.py`: `TCPServer.request_queue_size = 5`, passed to `listen()`;
  confirmed on 3.13.12.
- Node `net.Server.listen()`: default backlog 511 (https://nodejs.org/api/net.html#serverlisten).
- Linux `listen(2)` and `tcp(7)` (`tcp_abort_on_overflow` = 0 by default: a full accept queue
  drops the handshake ACK rather than resetting): https://man7.org/linux/man-pages/man7/tcp.7.html
- Earlier labs: `lab/2026-11-09-sse-relay.md` (single-stream relay, Nagle) and
  `lab/2026-11-09-cache-prefix.md` (captured request shapes used for `bodies.py`).

## What the planner should do next

1. **Small fix, high value:** in `copilot_shim/server.py`, use a `ThreadingHTTPServer`
   subclass with `request_queue_size = 128` (or `socket.SOMAXCONN`) and
   `daemon_threads = True`. Add a test: 32 simultaneous connects against the fake upstream
   with a held response, all complete in < 900 ms. This could go in the same PR as the
   one-line `TCP_NODELAY` fix from `sse-relay`.
2. Optional, low priority: `json.dumps(..., ensure_ascii=False, separators=(",", ":"))`
   to avoid the +59 % body growth on non-ASCII sessions; and drop the `deepcopy` in
   `rewrite()` by having the server parse a private copy. Neither is needed for the milestone.
3. Do **not** move to asyncio or multiprocessing for performance. Per-request overhead is
   ≤ 46 ms at 1M tokens, and GIL stalls are tens of ms.
4. When a Copilot login or real Claude Code binary is available, count simultaneous new
   connections during a 5-way subagent fan-out (a fake server that logs accept times). That
   confirms the real exposure of item 1.
